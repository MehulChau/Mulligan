Strong on mobile, app architecture, and statistics. Zero hardware experience (being learned as part of this project). Plays golf, is the target user. ## The vision (north star)
A cheap consumer device (~$15–30 BOM long-term) + phone app. You go to the range (or hit foam balls at home), the device measures your real swings, and you play simulated golf holes on your phone. **The range session IS the game session** — every real swing is a turn in the game. Not a stats app with a game bolted on; a game powered by real shots.

## Core architecture decision (do not revisit casually)
**Measure launch conditions in the first ~2 feet of flight; simulate everything else.**
This is how all affordable launch monitors work (vs. Trackman which tracks full flight with phased-array radar — not replicable cheaply, and not needed).

The measurement contract:
- **Ball speed** — measured by the device (camera + IR strobe multi-exposure)
- **Vertical launch angle** — measured by the device (same photo: slope of ball positions)
- **Horizontal start direction** — measured by the user's phone placed behind the ball (slow-mo video + CV). Not built yet.
- **Spin rate** — ESTIMATED from club selection + ball speed via lookup profiles (Trackman published averages). Real spin measurement (dimple rotation between strobe exposures) is a v2+ stretch goal, not a launch blocker.
- **Spin axis (draw/fade curve)** — estimated/simplified for v1.

Foam-ball mode insight: since we measure launch (not flight), foam ball launches can be scaled to what a real ball would have done → full simulated holes from living-room swings. Validate early that foam balls trigger/expose well (lighter, slower, less reflective).

## Hardware (inspired by PiTrac, open-source project — github.com/PiTracLM/PiTrac)
Single-camera v1, ~$220–250 total:
- Raspberry Pi 5 (4GB) — the brain
- Pi **Global Shutter** camera (must be global shutter — no motion distortion) + 6mm CS-mount lens
- High-power 850nm IR LED strobe + MOSFET driver (IRLZ44N), breadboarded for v0
- Laser diode (~$3) marking ball placement — known ball position massively simplifies CV
- Breadboard, jumpers, resistors, multimeter, one regular LED for testing
- Enclosure: none for v0 (breadboard on wood is fine); friend can 3D print later (PiTrac publishes enclosure files)

How it works: camera takes ONE long exposure while IR strobe fires several times → ball appears multiple times in one photo. Gap between ball images ÷ strobe interval = speed; slope of the line through them = launch angle. Device sits ~2ft to the side of the ball.

Hardware bring-up ladder (each rung independently testable):
1. Pi boots, SSH in → 2. camera takes a still → 3. laser on via GPIO → 4. MOSFET circuit blinks regular LED → 5. IR LEDs flash, camera sees it → 6. multi-exposure of a hand-rolled ball indoors → 7. real swings.
Status: parts being ordered; hardware is NOT the current workstream.

## Software architecture (4 layers)
1. **Capture & measurement** (on Pi): trigger, strobe sync, CV pipeline (find ball in each exposure → speed/angle). Build to run against static test images on a laptop, not only live camera. Not started.
2. **Shot pipeline / backend**: receives shot events, enriches (ballistics → carry/apex), persists. Data model: shots → sessions → clubs. Not started; can be local-first initially.
3. **The app / game** ← CURRENT WORKSTREAM. See below.
4. **Feature runway**: challenge modes, async multiplayer (ghost shots), daily challenge, GSPro connect API integration, shot classification, practice/proximity games.

## Current state: M3 done — the app can take a real device, still waiting on the device
The playable-hole MVP is being built in labeled milestones: **M0** (done, 2026-09-01) extracted and fixed the physics; **M1** (done, 2026-09-02) is one playable hole — pick a club, swing, watch the ball fly and come to rest, repeat until the green; **M2a** (done, 2026-09-04) adds putting, scoring, penalties, and lie-gated clubs so a hole produces a final score — with `estimateRollout()` still the M1 placeholder; **M2a.1** (done, 2026-09-04) replaces a flawed M2a workaround (routing every shot within 65 yards through the putting model) with real partial-swing wedges, so the 5–65 yard short game is actually played instead of resolved by a curve extrapolated 3x past its calibration; **M3** (done, 2026-09-04) is hardware readiness — the app can now receive a real shot over the network, from a defined wire protocol, with the workflow gaps (aim zeroing, data export) that only matter once a real device exists closed; **M2b** (not started) is the real surface-aware rollout model, still blocked on real range data for descent angle — M3 didn't unblock it, it's an orthogonal track. `tools/flight-lab.html` (moved from the repo root) is a thin UI shell that imports the built `@mulligan/physics` + `@mulligan/shot-source` modules — it carries no physics of its own. Build it with `npm run build:tools`, then serve the repo root over HTTP (`npm run tools`, http://localhost:4173/tools/flight-lab.html — ES module imports are blocked over `file://` by browsers) after any physics/club change.

Run the actual game: `npm run dev` (from repo root or `apps/web`), open the printed localhost URL. One hole, `SimulatedShotSource` stands in for hardware, skip-animation checkbox for fast iteration.

`packages/physics` (zero dependencies, SI in/out — see its `types.ts` for the coordinate-frame contract):
- Point-mass flight integration: drag + Magnus lift + gravity, semi-implicit Euler dt=0.004s (verified within 0.1% of converged; not worth a fancier integrator)
- Constants: m=0.04593kg, d=0.04267m, ρ=1.225, K=ρA/2m — named in `constants.ts`, the only place unit conversions (mph/yd/ft/deg/rpm ↔ SI) happen
- Spin ratio S=ωr/v; CL=min(0.34, 0.54·S^0.4); CD=min(0.34, 0.22+0.55·S); spin decay exp(−0.033t) — all 8 numbers live in `aero.ts` as an overridable `AeroParams`, not inline literals, so calibration is a data change, not a code change. **Still unretuned — no real range data yet.**
- Spin axis is now built in the *launch frame* (perpendicular to the aim direction), not world frame — the old code inflated side angle ~11% on any shot with a non-zero start line. Lift magnitude is scaled by sinTheta (angle between spin axis and velocity), not applied at full strength regardless of angle.
- Rollout was removed from the physics module entirely (`rollY`/`totalY` are gone). The integrator returns a complete `LandingState` (position, velocity, descent angle, remaining spin) and stops — rollout depends on the surface the ball lands on, which is M2's job, not the flight model's.
- Twelve club presets (ball speed mph / launch° / spin rpm) now live in `@mulligan/shot-source`'s `clubs.ts`, the source of truth (supersedes the shorter list this file used to carry): Driver 150/12.5/2800, 3-wood 140/13.5/3800, 5-wood 132/14.5/4400, 5-hybrid 120/16/5000, 6-iron 112/17.5/6250, 7-iron 106/18.5/7100, 8-iron 100/20.75/7850, 9-iron 94/23/8600, PW 86/26.5/9300, GW 79/28.5/9700, SW 72/31/10200, LW 66/33.5/10500.
- Golden regression values (straight-shot carry/apex/hang/descent per club) live in `packages/physics/tests/fixtures/golden.json`, not inline — they get deliberately replaced once real calibration data exists.
- Calibration harness (`@mulligan/shot-source/calibration`) is built and tested but **empty** — `MEASUREMENTS` has no real range data yet. Run `npm run calibrate` once Mehul's real gapping numbers are in; it fits `AeroParams` via a from-scratch Nelder–Mead optimizer (weighted on carry/apex/descent, descent weighted heaviest since it's what actually disambiguates the CL/CD split) and prints a before/after table — it never overwrites `DEFAULT_AERO` automatically. Running `npm run calibrate` against the empty array prints what's needed and stops, rather than erroring or silently fitting nothing. A second, separate array — `DISPERSION_MEASUREMENTS` — holds shot-group spread data (shot count, carry min/median/max or every shot, lateral spread, optional `swingFraction`) for tuning `swing.ts`'s `partialSwingPenalty` later; it isn't auto-fitted (no optimizer for it yet), it just gives the spread data somewhere structured to live. Both arrays have a commented-out filled-in example row directly above them. **`docs/range-session.md`** is the phone-sized checklist for the actual range trip: 3 clubs (driver, 7-iron, a wedge), 5 numbers each, plus a wedge-spread step (full-swing and half-swing buckets) for `DISPERSION_MEASUREMENTS`.
- Design language: turf/scorecard aesthetic — sage background, deep fairway green, sand-amber for ball flight, Archivo typeface. Keep this direction.

The `ShotEvent` the original brief described as a single type turned out not to be achievable as one type — the device physically can't measure club or spin, so it's now split:
- `RawShotEvent` — exactly what the Pi transmits: `{ballSpeedMph, launchDeg, timestamp, startLineDeg?, spinRpm?, spinAxisDeg?}`. Everything after `timestamp` is optional because the CV/spin-estimation subsystems don't exist yet.
- `ShotEvent` — what the game consumes: the same fields, all required, plus `clubId` and a `provenance` map (`measured` vs `estimated` per field) so the UI can be honest about what's real and the calibration harness knows which shots to trust.
- `enrichShot(raw, clubId)` in `@mulligan/shot-source` fills the gap: spin defaults to the club profile's spin scaled by swing-speed ratio, spin axis and start line default to 0 (straight) until their measurement subsystems ship.

## Milestone split — M1 vs M2 (revised 2026-09-02)
The original brief lumped "the game loop" and "the surface-aware shot resolver" into one M1. That packed too much into one milestone; split as follows. The distinction that matters: **M1 proves the geometry and the seam. M2 makes it a game.**

### M1 (done): hole model, renderer, shot sources, shot placement
- **Hole data model** — holes are data, not code: a `Hole` is a JSON file (`packages/game/src/holes/*.json`) so authoring new holes never needs a code change. Hole space is its own 2D yards coordinate frame, origin at the tee, `x` lateral (+right), `y` downrange (+toward pin) — deliberately different from the physics module's frame (x downrange, y up, z lateral); the conversion between them is isolated to `localToHole`/`holeToLocal` in `packages/game/src/resolver/rotate.ts`. Surface lookup (`fairway`/`green`/`rough`/`bunker`/`water`/`tee`/`out`) is point-in-polygon (ray casting, hand-rolled, no dependency), topmost-painted-surface-wins. `HOLE_1` ("The Bend") is the one hole for this milestone: a 400-yard dogleg-right par 4.
- **`ShotSource` seam** (`packages/shot-source/src/sources/`) — the interface hardware will eventually implement (`start`/`stop`/`onShot`), with three implementations: `ManualShotSource` (explicit numbers), `SimulatedShotSource` (dispersed shots per club, seeded/deterministic via a tunable `DispersionParams`; `PERFECT_DISPERSION` gives exact-preset shots for tests), and `ReplayShotSource` (replays a logged session back). An append-only `ShotLog` (localStorage, in-memory fallback) records every raw + enriched shot and where it ended up — built now, before real hardware needs it, since a reproducible bad shot is worth a lot when debugging later.
- **`startLineDeg`/`spinAxisDeg` are relative to the player's chosen aim heading, not an absolute compass direction** — documented on `RawShotEvent`/`ShotEvent` directly. Every bay at the range points the same physical way; the player aims in the app, the device only measures deviation from that.
- **Shot placement** (`packages/game/src/resolver/resolveShot.ts`) — runs the physics simulation, rotates the result into hole space, and reports both the landing point (carry) and rest point. Rollout is `estimateRollout()` (`resolver/rollout.ts`), a deliberately isolated, surface-agnostic placeholder — not the real per-surface model; M2 replaces it in that one file. Lie is detected (`landingSurface`/`restSurface`) and shown in the HUD but does not affect the shot.
- **Renderer + loop** (`apps/web`) — plain `<canvas>`, one static fitted camera (pin at top, tee at bottom, no pan/zoom), stylized top-down (Tiger Woods GBA energy, not 3D). React (`useReducer`) owns game state; the canvas owns drawing + the ~1.2s flight animation (with a skip-animation mode for fast iteration) and a short roll-to-rest. Aim is a slider (degrees off "aimed at pin"); 12 club chips; HUD shows distance/lie/shot number/expected carry (median of `DEFAULT_DISPERSION`, not the noiseless preset) plus, for the last shot, carry/total and per-field measured-vs-estimated provenance. Reaching the green shows "on the green in N" and a **Play again** button resets the session.
- Non-goals honored: no putting, no scoring, no par tracking, no "hole complete" state beyond the green message; no lie penalties; no multiple holes/course; no persistence beyond the shot log; no wind/elevation/slope; `@mulligan/physics` was not touched and `AeroParams` was not retuned (still no real range data).
- **Manual entry mode** (2026-09-03) — a Simulated/Manual toggle above the controls. Manual swaps the club-preset-driven flow for five sliders (ball speed, launch, spin, spin axis, start line, same ranges flight-lab.html used) feeding `ManualShotSource`, so every field is provided directly (all "measured" provenance) — this is the harness for typing in real device readings once hardware exists, not just for testing. Picking a club still loads that club's preset into the sliders as a starting point.
- **Mobile hardening pass** (2026-09-03) — this is a phone app first: safe-area insets, no accidental pinch/double-tap zoom, `touch-action`/tap-highlight tuned for a game screen (no text-selection callouts, no pull-to-refresh bounce), ≥40px touch targets, `apple-mobile-web-app-*`/`mobile-web-app-capable` meta for home-screen install. Found and fixed a real layout bug in the process: the canvas had no protected minimum height, so Manual mode's five extra sliders could crush it to a sliver (yardage-mark text overlapping into an unreadable blob). Fixed by giving `.canvas-wrap` a `min-height` floor and making `.controls` scroll internally instead (Swing button stays `position: sticky` so it's always one tap away regardless of scroll position).
- **Visual/animation polish** (2026-09-03) — ball now casts a ground shadow while airborne, with the ball itself lifted and scaled toward apex height (the shadow/ball gap is what actually sells height in a top-down view); eased roll-to-rest instead of linear; fairway/tee mowing stripes, bunker stipple texture, faint 50-yard markers, a landing-vs-rest marker during rollout, and prior shots now show a rest-position dot, not just the flight line.
- **Bounds-safety fix** — a wayward shot (wide dispersion tail, or an extreme manual entry) can land outside the hole's authored `bounds`; the camera now unions those bounds with whatever must stay visible each frame (current ball position, and the full path of an in-flight shot) so the ball can never render off-canvas. Confirmed live: an out-of-bounds 9-iron correctly expanded the frame instead of vanishing.

### Milestone split — M2a vs M2b (decided 2026-09-04)
The original M2 ("surface-aware resolver": real rollout + lie penalties + putting + scoring) got split again, for the same reason M1/M2 did: it packed a physics-calibration-blocked piece (real per-surface rollout) together with pieces that don't need it (putting, scoring, penalties, lie-gated clubs). Real rollout needs real range descent-angle data to be worth building — right now the physics module reports ~43–44° descent for every club (see the golden-value table above), which is a calibration gap, not a rollout-model gap, and building a detailed surface-rollout model against fake descent angles would be tuning noise against noise. So **M2a ships everything that makes a hole *finishable and scoreable* using the existing `estimateRollout()` placeholder unchanged**, and **M2b is the real rollout model**, deferred until real gapping/descent data exists.

### M2a (done, 2026-09-04): putting, scoring, and a hole you can finish
- **`@mulligan/physics` was not touched, `AeroParams` was not retuned, and `estimateRollout()` (`packages/game/src/resolver/rollout.ts`) was not touched** — confirmed via `git diff --stat` before committing. This was a hard constraint, not just a convention: M2a proves the game can produce a real score today; M2b is the only milestone allowed to touch rollout.
- **Auto-resolved putting** (`packages/game/src/putting/putting.ts`) — no tap-timing minigame, no aiming, no green reading. Probability of holing is piecewise-linear between anchor points (1ft→0.99 … 60ft→0.02) with exponential decay beyond the last anchor; a miss leaves `8–18%` of the putt distance (floored at 6 inches) so lag putts still leave something makeable. `MAX_PUTTS = 5` is a safety valve, not a rule — an amateur picks up after 5.
- **`isPuttable(surface, distanceToPin)`** gates when the game switches into putting mode: always true on the green, otherwise true within `FRINGE_PUTTING_DISTANCE_YDS`. **This constant was 65 yards, not a realistic fringe** — see the code comment in `putting.ts` for why; short version below. **Superseded by M2a.1 (below): it's back to a real 5-yard fringe now that partial-swing wedges exist.**
- **Scoring** (`packages/game/src/rules/scoring.ts`) — `summarizeScore(strokesToGreen, putts, par)` returns a labeled breakdown (eagle/birdie/par/bogey/double bogey/+N), shown on hole completion.
- **Penalties** (`packages/game/src/rules/penalty.ts`) — water and out-of-bounds both apply a 1-stroke penalty; OB is stroke-and-distance (replay from the exact previous position); water drops back 2 yards along the entry line from where the ball would have rested, so a penalty drop doesn't just re-hole the ball on the same spot.
- **Lie-gated club availability** (`packages/game/src/rules/clubAvailability.ts`) — restricts which clubs can be selected (rough bans driver/3-wood, bunker allows only wedges, green/water/out allow none — putt or drop instead); it never degrades a well-struck shot's outcome. When the ball comes to rest somewhere the current club is no longer legal, the game auto-switches to `firstAvailableClub`.
- **HUD/shot log** — HUD now shows live stroke count vs. par and a penalty callout when one fires; `ShotLogEntry` gained `strokeNumber`, `isPutt`, and `penalty` fields (and made ball-flight fields optional, since a putt entry has no raw shot).
- **A genuine dead end was found and fixed via Monte Carlo simulation, not by inspection.** The 12-club bag bottoms out at the lob wedge's fixed full-swing carry (~77 yards; M2a has no partial/finesse shots), so anywhere from a few yards up to ~70 yards from the pin, *every* available club overshoots — sometimes far offline rather than just long, because "aim at the pin" from close range can point almost sideways. Before the fix, ~10–25% of simulated rounds never finished (repeated overshoot/penalty loops). Fixed two ways: widened `hole-1.json`'s `bounds.maxY` (430→480, more room past the green) and widened `FRINGE_PUTTING_DISTANCE_YDS` from a realistic 5 yards to 65 — routing the entire "no club fits" zone through the putting mechanic as a deliberate stand-in for a missing chip/pitch shot. Confirmed via 50 simulated rounds: 0 failures after the fix (5 rounds at 3 strokes, 32 at 4, 13 at 5; mean 4.16, median 4, par 4). **The honest fix is a real partial-swing/chip mechanic for the 20–80 yard range — a candidate for M2b or a milestone of its own** — which would let the fringe threshold come back down to something that actually looks like a fringe.
- **This 65-yard workaround was itself wrong, caught by a second-opinion review before it shipped further.** Running the putting curve's own math out to 65 yards showed a ~0.02% hole-out chance and a flat ~3-stroke cost — not a putt, a toll. The curve's last calibrated anchor is 60 feet (20 yards); 65 yards is more than 3x past that, deep in unvalidated exponential-tail territory. Worse, the healthy-looking M2a score distribution (mean 4.16 on a par 4) was actively hiding this: most approach shots finished close enough that the toll only cost ~2 strokes, so nothing about the final numbers signaled that the entire 5–65 yard short game — the exact range-mat shot this product exists to serve — had been quietly deleted and replaced with a coin flip. See M2a.1.
- Non-goals honored: no green contours/slope, no multiple holes/course/handicap/multiplayer, `estimateRollout()` untouched, `@mulligan/physics` untouched.

### M2a.1 (done, 2026-09-04): partial-swing wedges, replacing the 65-yard putting workaround
Fixes the M2a.1 finding above with the mechanic M2a's own commit message had already named as the honest fix, rather than waiting for M2b. Confirms `estimateRollout()` and `@mulligan/physics` were still untouched.

- **`swingFraction` (0.3–1.0)** added to the simulated shot path only — `@mulligan/shot-source`'s `swing.ts` (`scaleClubForSwing`, `scaleDispersionForSwing`, both taking a tunable `SwingScalingParams`, same posture as `AeroParams`/`DispersionParams`: a data change, not a code change, once real partial-wedge range data exists). Ball speed and spin scale linearly with the fraction; launch angle nudges up slightly on shorter swings. This is a **simulated-mode-only concept** — the device only ever measures the ball speed a swing actually produced, so `swingFraction` never appears on `RawShotEvent`, and `ManualShotSource`/manual entry (which already lets you type the exact numbers directly) has no equivalent. `SimulatedShotSource.hit()` takes it as an optional third argument, default full swing — fully backward compatible.
- **A dispersion double-scaling bug shipped in the first cut of `scaleDispersionForSwing` and was caught by review before it went further: naively multiplying every sigma by the swing fraction made partial wedges preternaturally precise.** `ballSpeedNoiseSigmaPct`, `spinNoiseSigmaPct`, `startLineSigmaDeg`, and `spinAxisSigmaDeg` are all relative/angle measures that already produce a smaller *absolute* error on a shorter shot for free (2% of a slower ball speed, or 2° of a shorter carry, is already a small miss) — multiplying them by the fraction on top of that shrank relative error a second time, so a 30% lob wedge landed a measured ~0.5ft from target (p90 under 1ft) versus a real amateur's 10–15ft. It made the scoring zone a slider puzzle (set the number, get the number) with no uncertainty in it, in the one zone the whole product is about. **Fixed**: only the two *absolute-degree* launch sigmas (`launchAngleNoiseSigmaDeg`, `launchAngleThinFatBiasDeg`) still shrink with the fraction — legitimate, since a gentler swing has less strike-angle variance in absolute terms. The four relative sigmas instead get a new tunable `partialSwingPenalty` that *grows* them back up as the swing gets shorter — partial-swing distance control is, if anything, the hardest shot in golf, not the easiest.
- **The first `partialSwingPenalty` value (4) was itself wrong, caught by a second review pass.** At 4, proximity was non-monotonic across the wedge range — a full 73-yard lob wedge averaged ~13ft while an 80%-swing 50-yard shot averaged ~16ft, so a player could exploit the model by always clubbing down to a full swing on a shorter club instead of easing off a longer one. It also pushed 0.55% of 30%-swing `spinNoiseSigmaPct` samples negative, clamping to zero spin — a sign the sigma was over-scaled, not just aggressive. **Reduced to 2**, which is monotonic across the wedge range (measured ~3.4/6.6/9.7/12.6/13.0ft at 8/17/30/50/73 yards) with no negative-spin clamps observed. Documented directly on `partialSwingPenalty`, not just here: **even at 2, short-game proximity still reads tight against real amateur numbers, but that's a `DEFAULT_DISPERSION` baseline problem, not a partial-swing one** — the *full-swing* lob wedge itself lands ~13ft from 73 yards, where a real amateur is more like 25–35ft. The baseline was deliberately left untouched rather than tuned to compensate; wedge dispersion is directly measurable and belongs on the range-data list (`docs/range-session.md`), not adjusted blind. Re-verified against a 200-round Monte Carlo: mean 9.5ft / median 9.4ft / p90 15.5ft proximity for approach shots inside 60 yards — comfortably in believable range, though this number should be expected to widen once the baseline itself is corrected from real data.
- **`isWedge(clubId)`/`WEDGE_IDS`** moved to `@mulligan/shot-source`'s `clubs.ts` (the natural owner of club data) and re-exported; `packages/game`'s `clubAvailability.ts` now imports the shared list instead of keeping its own duplicate.
- **UI**: selecting a wedge in Simulated mode reveals a `SwingFractionSlider` (30–100%, 5% steps, same slider pattern as `AimSlider`) showing the live expected carry for the current fraction. Resets to full swing on every club change, same rule as the manual-entry sliders loading a club's preset. Hidden entirely in Manual mode (no swing-fraction concept there) and for non-wedge clubs. `expectedCarryYds()` in `apps/web` gained an optional `swingFraction` parameter, cache-keyed by `${clubId}:${fraction rounded to nearest 5%}` — same lazy-and-cached posture as the M1 fix, extended so a slider drag hits a handful of cache keys instead of minting a new one per pixel of movement.
- **`FRINGE_PUTTING_DISTANCE_YDS` reverted to 5 yards** (a real fringe) now that partial-swing wedges cover the gap for real, and `hole-1.json`'s `bounds.maxY` reverted 480→430 (it was only widened to accommodate the M2a overshoot dead end).
- **Reproducibility gap closed**: the putting RNG was seeded from `Date.now()` with the seed never stored or exposed, breaking the pattern `SimulatedShotSource.seed` established. Now the seed is captured once (`puttingSeedRef`) and logged on every putt (`ShotLogEntry.puttingSeed`) — a session can be reconstructed from any single logged putt, matching why the shot log exists at all. `ShotLogEntry` also gained an optional `swingFraction` field for ball-flight strokes.
- **Re-verified via Monte Carlo (200 simulated rounds, up from M2a's 50) after both dispersion fixes above**: 0 failures. Stroke histogram 25×3 / 119×4 / 55×5 / 1×6 (mean 4.16, median 4, par 4). **468 strokes played as real ball-flight shots vs. 364 resolved as putts (56.3%/43.8%)** — the number M2a couldn't produce honestly, because the short-game shots didn't exist to count. Wedge swing fractions actually chosen clustered at 35–45% (short greenside chips are the common case; a full-hole round rarely needs more club than that once the tee shot and approach are in play) — confirms the control is being used, not just present. Noiseless wedge carry curves came out close to hand-estimated expectations (e.g. lob wedge: 8.2yd at 30% swing, 77.2yd at 100%).
- Non-goals: no chip-specific dispersion model beyond the linear/penalty scaling above (a candidate for later tuning once real partial-swing range data exists), no swing-fraction control for non-wedge clubs, no change to `estimateRollout()` or `@mulligan/physics`.
- **This is as far as M2a work can responsibly go without real range data.** Every remaining decision — real rollout, whether a wedge holds a green, whether the whole thing feels like golf — depends on carry/apex/descent-angle measurements for a driver, a 7-iron, and a wedge from one real range session. Until that data exists, further tuning here is a model calibrated against a model, not against reality — which is exactly what let the 65-yard putting hack look like it was working. **Next real step is that range session, not another software milestone.**

### M2b (next, blocked on calibration data): the surface-aware resolver
Real rollout per surface (driver run-out vs. wedge stop — using the `LandingState` the physics module already returns, replacing `estimateRollout`). Needs real range descent-angle data first; building it against the current uncalibrated ~43–44°-for-every-club physics would just be tuning against noise.

### M3 (done, 2026-09-04): hardware readiness
Goal: when the Pi emits its first real shot, nothing on the app side should need to change. Six parts, all against a mock device (no Pi exists yet):

- **`docs/device-protocol.md`** — the wire contract the Pi will be built against, now **v1.1**. WebSocket, device-as-server/app-as-client (the Pi has a fixed address and stays up for a session; the phone sleeps and comes and goes — abstracted behind `ShotSource`, so BLE stays possible later without touching the game). A small versioned JSON message set (`hello`/`shot`/`status`/`ping`/`pong`), with a `capabilities` list on `hello` so the app never hardcodes what a hardware generation can measure. Restates the M0 measurement boundary as a protocol rule: **a value the device computed but didn't measure is a lie the app can't distinguish from a measurement.** Placeholder validation bounds (pulled from the manual-entry UI, not real mishit data). The original "Known gaps" list flagged one item that got closed same-day rather than deferred (see the `bootId` bullet right below) — a protocol gap is one JSON field before firmware exists and a coordinated cross-repo change after, so it was worth fixing before this doc becomes what a separate device repo gets built against. The other three gaps (status cadence, no session-end message, no authentication) are honestly stated and correctly still deferred.
- **`hello.bootId`** (v1.1, added same-day as a fix, not deferred) — an opaque string the device regenerates every boot; `deviceId` names the physical unit and stays stable, `bootId` doesn't. `NetworkShotSource` keys dedup on `(bootId, seq)`: a `hello` with a *new* `bootId` means a genuine reboot and resets the dedup tracker (since `seq` legitimately restarts at 0 there), while a `hello` repeating the same `bootId` (a plain reconnect) leaves it alone. A device that never sends `bootId` (v1.0) falls back to `seq`-only dedup and is logged once, not refused — a missing optional-in-practice field isn't a major-version mismatch. `tools/mock-device.ts` sends a real `bootId` and gained a fifth misbehavior (`reboot`: new `bootId`, `seq` restarted at 0, broadcast over the *same* still-open connection, deliberately not also dropping the socket — that path is already covered by `dropped-connection`) so the dedup-reset path is exercised by something before real hardware exists.
- **`NetworkShotSource`** (`packages/shot-source/src/sources/NetworkShotSource.ts`) — the fourth `ShotSource`, and the first genuinely asynchronous/stateful one (the three in-process fakes never needed this). Tracks connection state and device capabilities as separate subscribable channels a UI can build around (plain `onShot` isn't enough). Reconnects with exponential backoff, deduplicates on sequence number, validates every incoming shot (finite, in-bounds) before ever emitting it, answers ping/pong for liveness. **No WebSocket npm dependency** — reaches for the global `WebSocket` (present in both browsers and Node 22+) through an injectable factory, which is also what makes it fully unit-testable (16 tests) without a real server.
- **`tools/mock-device.ts`** — a real WebSocket server speaking the protocol from the device side exactly as v1 hardware will (`hello` advertising only `["ballSpeed","launch"]`). `npm run mock-device`, driven by keypress: `[Enter/s]` one shot, `[n]` toggle auto-fire, `[m]` cycle misbehaviors (malformed JSON, duplicate seq, out-of-range value, dropped connection), `[q]` quit. Two testing-only env vars: `MOCK_DEVICE_AUTOSTART_SEC` (drives it in a headless/non-TTY context, no keypress) and `MOCK_DEVICE_START_LINE_OFFSET_DEG` (injects a fixed start-line offset + advertises `"startLine"`, so aim-zeroing has something real to calibrate against before the phone-behind-ball CV subsystem exists — never representative of real v1 hardware). **This mock is not throwaway** — it's how you tell whether a future bug is in the Pi or the app.
- **Source selection UI** — `Device` joins `Simulated`/`Manual` in `SourceModeToggle`. `DeviceSourcePanel` (address field persisted to localStorage, Connect/Disconnect, live connection state, capability badges reusing the HUD's measured/estimated styling) and a clear fallback message when disconnected mid-round ("switch to Simulated or Manual to keep playing") rather than stranding the player. Both panels are deliberately compact — touched once at the start of a session, never again, so they don't compete with the club chips or the Swing button.
- **Aim zeroing** — `AimZeroPanel` + `DeviceSessionState` in `gameState.ts`. One tap to start, one real shot toward a fixed physical target to sample, one tap to confirm; the sample shot is diverted before it reaches `resolveShot` and never counts as a stroke. Only `startLineDeg` gets the `sessionZeroDeg` correction, deliberately never `spinAxisDeg` (spin axis is already relative to the ball's own flight path, not the device's absolute mounting rotation — documented in both `gameState.ts` and the protocol doc). The zero and the device connection both survive "Play again" — re-pairing and re-zeroing every hole would be exactly the friction this milestone exists to remove.
- **Session export/import** (`packages/shot-source/src/log/sessionExport.ts`) — `exportSession` bundles a `ShotLog` session (every `RawShotEvent`/`ShotEvent`/provenance/rest position) plus caller-supplied metadata the log itself doesn't know about (aim zero, simulator seed). Real Export/Import controls in the app header (small, end-of-session use only) — export downloads JSON via a Blob; import loads a file's entries into the live `ShotLog` under their original session id. Round-trip proven by `packages/game/tests/sessionReplay.test.ts`: play a logged sequence, export it, import it into a fresh log, replay every raw shot through `ReplayShotSource`, re-resolve each one in original order — every rest position, landing surface, and rest surface matches exactly.
- **`npm run rescale-clubs`** — `CLUBS` describes a generic ~150mph-driver player, not Mehul; a good aero fit corrects the flight model, not the presets. Takes measured ball speed/launch for driver, 7-iron, and one wedge (`--wedgeClub=pw|gw|sw|lw`), scales ball speed by the measured/baseline ratio interpolated by club position between anchors (flat-extrapolated past the last one), scales spin by that same ratio (matching `enrichShot`'s existing spin-estimation assumption). Launch angle: **the measured delta is applied at full strength on the three anchor clubs themselves — `docs/range-session.md` already has you take a median across 8-10 shots there, so a directly measured value is real evidence, not noise to discount.** Damping (0.5x) applies only to the nine clubs that weren't measured, where the anchor's delta is being extrapolated to a club never hit — a different, weaker claim than what was actually observed. The tool prints both the raw and damped numbers at each anchor so which one applies where is never hidden. Same posture as `npm run calibrate`: prints for review, never writes `clubs.ts`. Documented in `docs/range-session.md` as a post-session step — and a `clubs.ts` change means the golden fixture needs a deliberate, reviewed regeneration afterward, never automatic.
- **Live-verified end to end** against the mock device, not just unit-tested: connect, capability badges, a real shot played through Device mode, aim-zero capture and confirm without counting as a stroke, disconnect-mid-round showing the fallback message, auto-reconnect with the zero retained, all four misbehavior modes handled with zero console errors and no phantom/duplicated shots, and export→import round-tripping through the actual browser download/upload path.
- Non-goals honored: no physics changes (`@mulligan/physics`/`AeroParams` untouched), no `estimateRollout()` changes (still M2b), no BLE, no device-side/Pi code, no cloud/accounts/hosting.

Handicap, challenge modes, and ghost multiplayer stay in the feature runway, after M2b and M3.

## What's next (read this before starting new work — 2026-09-05)

**The app is done pending real data.** M3 shipped 179 passing tests, `verify-m0.ts` green, tagged `m3`. Every remaining decision in *this* repo is downstream of measurements that don't exist yet — there is no more engineering to do here until a real range session happens. If you're a future session picking this repo back up: don't go looking for the next feature to build. Read this section first.

- **M2b (surface-aware rollout) is blocked on the range session, not on engineering.** `estimateRollout()` is still the M1 placeholder. The aero model saturates above roughly 6000rpm, so predicted descent angle comes out ~43–44° for all twelve clubs — a driver and a wedge land at the same angle in the model, which means a real per-surface rollout built on that input literally cannot distinguish a driver's run-out from a wedge stopping on the spot. Building it now would be tuning a rollout model against noise, not physics. `docs/range-session.md` is the unblocking step, in order: `npm run calibrate` (fits `AeroParams` to real carry/apex/descent), then `npm run rescale-clubs` (fits the twelve club presets to the same real clubs), then a **deliberate, reviewed** regeneration of the golden fixture — never automatic, both tools print for review and never write.
- **Also unresolved from the same range data: `DEFAULT_DISPERSION` for wedges is too tight.** A full lob wedge currently finishes ~13ft from target where a real amateur is 25–35ft (see the M2a.1 section above for the full story). `partialSwingPenalty` is compensating for a baseline problem rather than fixing it — it was deliberately left alone rather than tuned further blind. The wedge-spread step in `docs/range-session.md` (`DISPERSION_MEASUREMENTS`) exists specifically to fix this with real numbers instead of another guess.
- **Active work has moved to a separate repo: `mulligan-device` (Python, `~/Documents/mulligan-device`).** It measures ball speed and vertical launch angle from a single strobed photograph containing several exposures of the ball, and will eventually send those over the WebSocket protocol in `docs/device-protocol.md` (this repo owns the canonical copy — see the note at the top of that file). It never simulates ball flight, never knows about clubs, and never computes carry — that boundary is the protocol doc's own rule (*"a value the device computed but didn't measure is a lie the app can't distinguish from a measurement"*). When it's ready, it connects to this app as a `NetworkShotSource` and **nothing in this repo needs to change** — that was the entire point of M3.

**Do not touch `@mulligan/physics`, `AeroParams`, or `estimateRollout()`** until real range data exists to justify a change. If you're tempted to "improve" the rollout placeholder or retune dispersion without that data, don't — re-read the M2a.1 section above for what happened last time a model got tuned against itself instead of reality.

## Tech stack (decided 2026-09-01, for v1 game)
npm workspaces monorepo:
```
Mulligan/
├── packages/
│   ├── physics/       @mulligan/physics — pure TS, zero deps, the ball-flight model + calibration config
│   ├── shot-source/    @mulligan/shot-source — clubs, RawShotEvent/ShotEvent + enrichShot, the calibration harness, and (M1) SimulatedShotSource (depends on physics)
│   └── game/           @mulligan/game (M1) — hole data model, point-in-polygon surface lookup, hole JSON, shot placement (depends on physics + shot-source)
└── apps/
    └── web/            @mulligan/web — Vite + React 18 + TS, canvas rendering for the hole/ball-flight view
```
- **apps/web**: Vite + React + TypeScript, plain `<canvas>` for game rendering (no game-engine library) — matches flight-lab.html's approach, keeps deps minimal. React owns the HUD/club-picker/scorecard UI, which is the part most likely to carry over to React Native later.
- **packages/physics** and **packages/shot-source** are plain TS with no React/browser APIs — this is what lets the same math run in the web app, a future backend, and tests unchanged. When phone (React Native/Expo) or the Pi backend arrive, they become new consumers of these same packages, not rewrites.
- Package manager: npm (workspaces). Test runner: Vitest. TypeScript strict mode everywhere. Packages resolve each other directly via source (package.json `main`/`types` point at `src/index.ts`) — no TS project-reference/composite build step; that was tried during M0/M1 and dropped because it required manually rebuilding a `dist/` that nothing in the real toolchain (Vite, esbuild, Vitest) ever reads, and a stale one silently shadowed live source during typecheck.
- Device↔phone link will be BLE or WiFi from the Pi; abstract behind the ShotEvent interface so transport is swappable.
- Decide on React Native/Expo for the mobile port once the web game loop is proven — not committed yet.
